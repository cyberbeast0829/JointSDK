# 诊断 —— 错误位 / 字节序 / 单位 / 遥测

## 1. ⚠ 别信"错误名"，去看**原始位**

设备摘要里的 `err_name = "CAN_TIMEOUT"` 会把**看门狗超时**和**急停**混成同一个名字
（固件 `detect_error_code()` 把两种都映射成 `ERR_CAN_TIMEOUT`）。

⇒ 看到它就去查波特率/线缆，会白费几个小时。

**正确做法**：

```
jsdk_get_state(node=...)          # 取各子系统的原始位图 (*_hex)
jsdk_get_fault_detail(node=...)   # 六类分项：motor/encoder/controller/sensorless/system/axis
```

⚠ 另外注意：**MIT 4-bit 错误码、心跳 5-bit 子系统位、32-bit 子系统位图是三套不同的东西**，
别混着读。

### 看门狗语义（容易读反）

- `break_timeout == 0` = **超时检测被禁用**（**不是**"100 ms"，那是旧固件行为）
- 非 0 = **真的武装**：停发控制帧超过该时长 → `ERROR_CAN_BUS_FAILED` + `disarm()`
- ⚠ `CURRENT_CONTROL` **不喂看门狗** ⇒ 纯电流客户端 **CAN 掉线也不停机**（安全缺口）

### 清故障

```
jsdk_fault_reset(node=..., confirm=true)
```

⚠ **原因还在，故障会立刻回来 —— 这是正确行为，不是失败。**
清完重新 `jsdk_get_state`；若又出现，去查根因（温度/编码器/机械/急停）。

## 2. ⚠ 字节序：两种并存

同一个设备上**两种字节序同时存在**。搞混的后果是"**看着像数字的静默错值**"，
不会有任何报错。

| 内容 | 字节序 |
|---|---|
| 参数值（`0x20`/`0x21` 载荷） | **小端** |
| JSON 描述符里的数值 | **小端** |
| 帧字段（CAN ID 位域、`EpID`、`Offset`、`ReqLen`） | 大端 |
| 查询响应（`0x41`/`0x46` 等） | 大端 |

**症状**：`gear_ratio` 读出 `8.9e-41`、`node_id` 读出 `16777216`。

**自检技巧**：如果只有 `u8` 参数读得对、其它全错，基本就是字节序问题。

⇒ SDK 已处理（`cb_le_*` 管值、`cb_be_*` 管帧字段）。**不要自己再解一遍字节**。

## 3. ⚠ 单位：同一物理量，不同帧不一样

| 来源 | 位置 / 速度 |
|---|---|
| MIT 应答 / 所有控制应答 | **输出端** rad、rad/s |
| `0x41` 查询、心跳 | **电机端** turns、turns/s |
| `TORQUE` 控制帧 | **电机端** N·m（MIT 的 `tau` 是**输出端**） |

⇒ 这是最容易静默算错的地方：拿心跳的 turns 当 rad 用，会差 $2\pi \times \text{gear\_ratio}$ 倍。

**位置真值**：读端点 `axis0.encoder.pos_estimate`（**电机端 turns**）。

⚠ **多圈关节不能用 MIT/查询应答做位置反馈**：那些帧是 16-bit 定点，
量程只有 ±`mit_max_pos`（本机 12.5 rad）。**超出量程时应答只回量程上限值**
——看着像"位置不动了"，其实是量程饱和。

## 4. 遥测怎么读（`jsdk_get_telemetry`）

```
jsdk_get_telemetry(node=..., duration_ms=1000, rate_hz=10)
```

返回 `samples` + `summary`。**`summary` 是可核查的统计，不是结论** —— 自己判断。

判读要点：

| 字段 | 怎么用 |
|---|---|
| `age_ms` | **判新鲜度用这个**。远大于预期上报周期 ⇒ 反馈不新鲜（先看链路，别解读数值） |
| `usable_samples` / `errors` | 丢样比例高 ⇒ 链路或周期太紧 |
| `t_motor_C` / `t_fet_C` | 是否**持续爬升**（爬升 = 负载/散热问题） |
| `vbus_V` | 是否在合理范围、是否跌落（跌落 = 供电问题） |
| `pos.span` / `first` / `last` | 位置是否真的在动、朝哪个方向 |
| `axis_error_values` | 出现过非零错误位 ⇒ 去 `jsdk_get_fault_detail` |

### ⚠⚠ 不要用 `valid` 判新鲜度

`valid` 是**每周期**旗标，**任意时刻采样约 50% 为真** —— 用它判新鲜度会得到随机结论。

⇒ **判新鲜用 `age_ms`。**

（仿真环境下反馈时间轴与墙钟不同步，`valid` 的分布更没意义。）

## 5. 采样率的取舍

⚠ 采样率过高会把 slcan 挤爆（115200 上限约 380 次交换/秒）→ 后段全超时。

- 慢速链路（slcan）：`rate_hz` 用 **10 左右**
- 要看快速瞬态（如堵转、抖动）：先确认链路够快（SocketCAN / FD）

⚠ 使能后设备上报率会暴涨（实测失能 **10 帧/s** → 使能 **~888 帧/s**），
USB-CDC 的 slcan **撑不住**（长期饱和）；**闭环请用 SocketCAN**。

## 6. 读数"看着正常"也可能有问题

⚠ **不要因为工具返回 `ok: true` 就认为一切正常。** 本工具链的设计是**如实报告**，
不是**替你判断**：

- `ok:true` 只表示"这次调用没出错"
- 数值是否合理，要你自己对着上面的表判断
- `note` / `hint` / `warnings` 字段里藏着关键提醒 —— **要读**
